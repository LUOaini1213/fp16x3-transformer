01

The contract we are graded against

The harness swaps a UserOptimizedTransformer in for the reference BaselineTransformer and compares them across 14 shapes. An entry passes a trial only if every output element satisfies abs_err ≤ 0.002 or rel_err ≤ 0.02. One failing element fails the shape. Any NaN or Inf is a hard fail. Latency is only measured if accuracy passes first, so speed is worth nothing without correctness.

Weights are copied with strict=True, so we keep every baseline submodule and parameter name and rewrite only the forward compute. Nothing is added to the state_dict; the comparison stays apples to apples.

That or in the tolerance rule matters more than it looks, and it comes back in section 5.

02

The wall at 100,000 tokens

The baseline computes attention the explicit way: materialize scores = Q·Kᵀ with shape [B, H, S, S]. For shape 14 that is 32 × 16 × 10⁵ × 10⁵ = 5.12×10¹² elements — about 20.5 TB in fp32. No GPU holds that. The baseline does not run slowly on this shape; it does not run.

F.scaled_dot_product_attention (memory-efficient backend) never materializes that matrix. Same mathematics, O(S) memory instead of O(S²). On the graded hot path there is no padding, so causality goes through is_causal=True with attn_mask=None and the mask is generated inside the kernel — which is the only option available, since a dense [S, S] mask at S=100000 would itself be 10 GB.

That gets the attention inside memory. It did not get the shape to run, and the reason was somewhere else entirely.

The bug was in the concat

Batch-chunking the forward and collecting the pieces in a list ends with torch.cat, which holds the chunks and the joined [32, 100000, 1024] result at the same time — a second ~6.5 GB allocation on a card that already had the 6.5 GB input resident. The failure read as Tried to allocate 6.10 GiB and looked like an attention problem. Writing each chunk straight into a preallocated output removed the second copy, and the shape ran.

The chunk size is planned from VRAM that is actually free at runtime (cuda.mem_get_info plus the allocator's reserved-but-unused blocks), minus the output buffer, divided by the roughly eight activations a block keeps live at once. If the estimate is still optimistic, the chunk halves and the pass restarts, so a bad guess degrades instead of failing.

Result on a free 16 GB P100: the full-length forward completes in 293 s at 10,907 tokens/s, peaking at 14.61 GB of a 17.06 GB card, with chunk_bs=1. On a T4 — same memory-efficient backend, but its fp16 tensor cores carry the natively-fp16 matmuls — the same forward takes 204 s at 17,402 tokens/s at a 14.17 GB peak — on a card holding only 15.64 GB in total, tighter than the P100, and it still fits.

That run is fp16, and for this shape that is forced rather than chosen: an fp32 input is 32 × 100000 × 1024 × 4 B = 13.1 GB and the output is another 13.1 GB — 26.2 GB committed before a single activation. Correctness for this shape is established separately, in fp32, at a truncated seq_len where the baseline can run: PASS at max_abs 1.2e-6. SDPA's mathematics does not depend on S.

04

Results across two free GPUs

Kaggle's API hands out a Tesla P100 unless machine_shape asks otherwise. That card is sm_60: Triton will not build, so torch.compile never engages. Asking for NvidiaTeslaT4 turns compilation on. The attention kernel is the same on both cards: PyTorch's flash backend is fp16-only and needs sm_80+, and a probe forcing each backend alone (results/kaggle_t4_probe.log, results/kaggle_p100_probe.log) finds flash = no for every dtype and head dimension on both GPUs. No run here used FlashAttention; every call used the memory-efficient backend — the O(S)-memory kernel shape 14 actually depends on.

A ratio has two sides

The T4's baselines are slower than the P100's — 324.7 ms against 168.6 ms on shape 13. The P100 has more fp32 throughput and roughly twice the memory bandwidth. Our ratios improve on the T4 anyway, because the optimized path gains compilation there while the baseline stays bandwidth-bound — the attention kernel is identical on both cards. Worth stating which side moved rather than banking the bigger number.

05

fp16 is nearly twice as fast. We ship fp32.

Turning on internal fp16 (T3_AUTOCAST=fp16) passes all 13 shapes at a median 4.014×, up to 11.53× on shape 13. It is one environment variable. We ship it off, and the reason is a single number.

fp32 — shipped worst max_abs 1.91e-6
1049× inside the gate
fp16 — opt-in worst max_abs 2.04e-3
0.98× — already past it
error → atol = 0.002

The fp16 worst case is max_abs = 0.0020388, on shape 6. That has already crossed atol = 0.002. It passes only because the gate is abs ≤ 0.002 or rel ≤ 0.02, and that particular element happened to have a reference value large enough (|ref| ≥ 0.102) for the relative branch to catch it.

Nothing makes that repeatable. Put the same error on a near-zero reference and the element fails — and one failing element fails the shape and forfeits the speed score entirely. The trade is roughly twice the speed for a correctness margin of essentially zero on a hard gate. We took the 2.29× that sits 1049× inside tolerance and left fp16 as a documented, measured flag. The apparent middle ground — fp16 attention with fp32 FFN and LayerNorm — was measured too: 2.953× at a worst error of 1.72e-03, a margin of 1.17×. Moving everything after the attention to fp32 recovered almost nothing, which puts the error floor inside the fp16 attention matmuls themselves.

Where we were wrong

The repository previously asserted that fp16 “breaks the strict atol=0.002 gate”. Measuring it showed that is false — fp16 passes all thirteen shapes. The conclusion survived; the justification did not. The real reason to ship fp32 is margin, not failure, and we only know that because we ran it.

06

The hand-written kernel, and why it is switched off

Composing scaled_dot_product_attention with torch.compile is library work, not kernel work, on a track named for kernels. kernels/fused_layernorm.py closes that gap: a fused residual-add + LayerNorm in Triton. The target was chosen on purpose — nn.LayerNorm alone is already a tuned CUDA kernel and rewriting it is a predictable loss, but eager PyTorch does not fuse the pre-norm pattern a block repeats twice per layer, where the add and the norm each traverse the whole [B,S,D] activation. Fusing them takes four passes down to two.

It wins its own benchmark, and we matched the compiler rather than beat it

As a raw launch, enabling it forced torch.compile off — a raw Triton call breaks the graph — and end to end it lost: 1.929× against the 2.282× with compilation fixed on. So we registered it through torch.library.triton_op, which lets Inductor schedule it inside the compiled graph. That recovered most of the loss: 2.190×, still 13/13 PASS. It still does not win. Inside the graph, Inductor's own fusion of these two ops is within ±5% of ours on the memory-bound shapes and wins outright on the small ones, where a custom op is an opaque wall the compiler cannot fuse across and dispatch costs 30–70 µs a call. The kernel exists, is correct, composes with the compiler, and ships disabled — with every number published rather than the flattering one.

07

The attention kernel: accuracy won, speed lost

The precision sweeps put the error floor inside the fp16 attention matmuls. It is not accumulation — cuBLAS and SDPA already accumulate in fp32 — it is five fp16 storage roundings. kernels/attention.py keeps everything in fp32 and rounds only the tensor-core operands, and with SPLIT=3 splits each operand into fp16 hi/lo halves so the product is three MMAs at ~2−22 relative error.

08

fp32-accurate GEMMs on the fp16 tensor cores

A kernel-level profile of the shipped forward put fp32 cuBLAS SGEMM at 44–89% of GPU time on shapes 1, 6 and 8. A T4 has no fp32 tensor cores and no TF32; its fp16 tensor cores are eight times faster and were idle. fp16 inputs had already failed the gate (section 05). fp16 arithmetic with compensation passes it: each operand becomes an fp16 hi + lo pair, exact to about 2-22, and one cuBLAS GEMM with K tripled — [a_hi | a_hi | a_lo] · [w_hi ; w_lo ; w_hi]T — accumulates the three cross terms in fp32 with an fp32 output. The weight is pre-scaled by a power of two so its lo part is a normal fp16 number; alpha = 1/s in the epilogue undoes it exactly.

The split has to be free or it eats the win: a PyTorch-side split cost exactly what the faster GEMM saved. So the tiled Triton kernel that produces each activation — LayerNorm, add+LayerNorm, GELU — writes the hi/lo pair directly, registered as triton_ops that Inductor schedules inside its graph. The GEMM has to be bare: cuBLAS's epilogue for the bias and the weight scale measured 40–90% slower than a plain mm, so both ride in the neighbouring kernels instead. And the operand order matters: Turing's tensor cores accumulate with truncation, so summing the two tiny cross terms first — a change of column order — cut the error 1.6–3.7× at zero cost. All four GEMM sites take the path: the operator table said two of them should not, and three end-to-end runs said otherwise.

What it costs. 9.5e-06 at K=1024 instead of SGEMM's 3.2e-06 — 210× inside the gate, not a thousand. The CPU emulation of the identical arithmetic lands ~1.3e-6 at every K, so the residual is the Turing tensor core's truncating accumulator, growing linearly with K; the lo-first order halves it, split-K (T3_X3_SPLITK) halves it again at twice the GEMM cost and stays an option. Four variants lost and are published: a PyTorch-side split, a two-GEMM form, the cuBLAS epilogue, and a first-forward tuner for the fp32/fp16x3 choice (T3_LINEAR=auto, 2.299× / 2.214× over two runs, retired at the noise floor). The fp16 range is guarded: a bound from the weights refuses the path where a LayerNorm or GEMM output could leave it, and the first forward's output is checked once, never inside the timed region.

A measurement bug, found late. Earlier versions of every table here were taken with torch.compile silently inactive on shapes 6, 8 and 13: the sweep runs all shapes in one process, each costs Dynamo two compiled variants, and past eight it stops compiling without a word. The harness runs one shape per process and never gets there; the model now raises the limit itself, and every number on this page was re-measured after the fix.

09

Two things that look like defects and are not

--dtype bfloat16 fails the gate

It does: 6131 of 131072 elements, max_abs 0.047. So does the reference compared against itself recomputed in fp32 — 7603 elements, the identical max_abs. bf16's ulp near 1.0 is 0.0078, four times coarser than atol=0.002, so no implementation that reorders a single operation can hold that gate in bf16. The graded configuration is fp32, where we sit three orders of magnitude inside it.

The padded path rebuilds an O(S²) tensor

True. When a real padding mask is supplied, the fallback materializes a dense [B, 1, S, S] additive bias, giving back exactly the memory SDPA exists to avoid. The graded path runs padding_ratio=0, where masking is kernel-generated and no bias is built, so the fallback only has to be correct at the small S where a mask is actually supplied. Making it memory-efficient too is unfinished work, not a solved problem we left out.

10

Reproducing this

Development happened on a laptop with an Intel iGPU and no NVIDIA card, so every GPU run was pushed headlessly to Kaggle and pulled back. The numbers above come from that path, and the raw kernel logs are committed beside the tables so each figure traces to the run that produced it.

python scripts/build_kaggle_selfcontained.py --accelerator NvidiaTeslaT4
kaggle kernels push  -p .kaggle_upload/kernel_sc
kaggle kernels output wenjiluo/track3-bench -p .kaggle_out
python scripts/parse_kaggle_log.py .kaggle_out/track3-bench.log

The builder inlines the unmodified harness, the optimized model and the sweep driver into a single script, so the kernel needs no dataset attached. On a machine that already has a GPU, the same model runs under the official harness directly with python run_all.py --shapes 1-13 --device cuda --dtype float32.

One trap worth documenting

The accepted machine_shape values — NvidiaTeslaT4, NvidiaTeslaP100, Tpu1VmV38 — appear only in the SDK docstring for ApiSaveKernelRequest. An unrecognised value is silently normalised back to a generic "Gpu" and lands on a P100, so a wrong guess looks exactly like a successful request. Verify by reading the device name back out of the running kernel.
